# 0004 送信と受信を分け、送信から出す

## 状況

M1 仕様の見取り図では M2 を「同期」ボタン（fetch → pull --rebase → push）としていた。ユーザーは、
pull と push を一つにまとめると競合を起こしやすいので避けたいとした。語彙は「同期」をやめて「送信 / 受信」にした。

## 選択

- 送信（push）と受信（pull）は別のボタンにする。M2 の最初は送信だけを出す（バックアップの目的はこれで足りる）。
- 送信先は `origin` リモート。Shiori はリポジトリを作らず、トークンも持たない。利用者が空の非公開リポジトリを作って
  URL を貼る。設定は `.git/config` だけに書き、`ProjectSettings/Shiori.json` には持たない。
- 「確認する」は `git ls-remote --heads` だけを使い、何も書かない。空 / このプロジェクトの保存だけ / 知らない保存あり、を区別する。
- 送信は `git push --porcelain -u origin <branch>`。強制 push はしない。送信先が先に進んでいれば拒否され、何も変えない。
- 送信していない保存の数は `refs/remotes/origin/<branch>..HEAD` から数える。ネットワークは使わない。
- ネットワーク操作には時間制限を付ける（ls-remote 60 秒、push 30 分）。git の出力（LC_ALL=C）から原因を
  認証 / 見つからない / 接続 / 拒否 / 大きすぎる / 時間切れ に分け、平易な文で出す。
- はじめの設定に「送信先（任意）」を最後に置く。完了の条件には含めず、最初の保存のあと一度だけ案内する。

## 理由

- 一方向の送信は競合を作らない。分かれた履歴の扱いは M5 で決める。
- 認証は資格情報マネージャーに任せる方針（CLAUDE.md）を守れる。

## 追記: 受信（同じ M2 の後半）

- 受信は `git fetch --prune origin` のあと `git merge --ff-only` だけ。保存していない変更があれば止める。
  この PC と送信先の両方に相手にない保存があるとき（履歴が分かれたとき）と、共通の履歴がないときも、何も変えずに止める。
- 作業ツリーを書き換えるので、戻すと同じく自動更新を止めてから同期的に Refresh し、変わった開いているシーンを読み直す。
- 裏での確認は、かんたんモードの更新のあと最大 5 分に 1 回。`-c credential.interactive=false` と
  `core.sshCommand=ssh -o BatchMode=yes` を付けた fetch（20 秒まで）で、サインインが要るときは黙って諦める。
  比べた結果（受信できる数 / 分かれている）は手元の refs だけで数える。

## 捨てた案

- 「同期」1 ボタン: ユーザーの判断で不採用。
- Shiori から GitHub API でリポジトリを作る: トークンを扱うことになる。
- 窓を開いたときの裏での fetch（受信の知らせ）: 受信と一緒に入れる。サインイン画面を勝手に出さない仕組みが要る。
